Most [Open Payments](https://openpayments.dev/) examples run on a server or in a browser. But a lot of people send money from their phone. So we asked a simple question: **can a mobile app use Open Payments to send money from the user's own wallet, without making the user log in again for every payment?**

The answer is yes. In this post we build a small proof of concept (PoC) with [Expo](https://expo.dev/) and React Native. The app runs against the [Interledger Test Wallet](https://wallet.interledger-test.dev/), so you can use play money.

This is a hands-on guide. If you join the Interledger hackathon in Colombia this weekend, you can follow it step by step, run the app, and build your own idea on top of it.

---

## What you will build

The app has four tabs:

- **Wallet**: connect your wallet. The phone creates its own key, adds it to your wallet, and your wallet confirms that you own the address.
- **Send**: a list of contacts. Pick a contact, type an amount, tap **Proceed**, approve the payment in your wallet, done.
- **History**: every transfer made from the app, with live status from the wallet.
- **Budget**: a second model, where a server holds the key and the user approves a monthly budget once. We don't cover it in this post.

## Before you start

You need:

- **Two Test Wallet wallet addresses**. Sign up at [wallet.interledger-test.dev](https://wallet.interledger-test.dev/), finish the (simulated) KYC and add some play money. One address is yours (the sender). The other one is a contact (the receiver). A different currency is fine, for example USD to MXN.
- **Node.js 22** and **npm**.
- **Xcode** with an iOS Simulator, or Android Studio with an emulator. The app uses a development build, not Expo Go, because it uses native modules.

## The big picture

Before the code, here are four ideas that make the whole thing work.

**1. The client is the user's own wallet address.** In Open Payments, every request is signed by a _client_. The auth server finds the client's public key at `{walletAddress}/jwks.json`. In this app, the client is the user's own wallet address, and the key lives on the phone. This is the same model the [Web Monetization extension](https://github.com/interledger/web-monetization-extension) uses. There is no backend.

**2. The phone signs every request.** The official JavaScript SDK depends on Node.js crypto, so it does not run in React Native. Instead, the app has a small client (about 200 lines) built on `fetch`. It signs each request with [HTTP Message Signatures](https://openpayments.dev/identity/http-signatures/).

**3. The wallet runs in an in-app WebView.** Login and consent happen on the wallet's own web pages. A WebView keeps its cookies when the app restarts. So the user logs in **once**, inside the app, and after that every consent screen opens directly. The Test Wallet session lasts about one month.

**4. Open Payments only supports redirects.** The auth server sends the user to the wallet's consent page, and then redirects back to a `finish` URI with an `interact_ref` and a `hash`. Our finish URI is `rafikiupclose://op/finish`. The WebView catches this redirect, closes, and gives the values to the app.

## Step 1: Create a key on the phone

The app creates an Ed25519 key pair with [`@noble/ed25519`](https://github.com/paulmillr/noble-ed25519). We give the library a synchronous SHA-512 function, because React Native (Hermes) has no WebCrypto.

<CodeBlock
  language="typescript"
  title="src/op/keys.ts"
  code={`import * as ed from '@noble/ed25519'
  import { sha512 } from '@noble/hashes/sha2.js'

  ed.hashes.sha512 = sha512

  export function publicJwk(key: DeviceKey): Jwk {
    return {
      kid: key.keyId, // a random UUID
      kty: 'OKP',
      crv: 'Ed25519',
      alg: 'EdDSA',
      x: toBase64Url(ed.getPublicKey(key.privateKey))
    }
  }`}
/>

The 32 random bytes come from `expo-crypto`. The private key goes to the iOS Keychain (or Android Keystore) with `expo-secure-store`. It never leaves the phone. Note: the iOS Secure Enclave does not support Ed25519, so the Keychain is the best option here.

## Step 2: Sign every request

Open Payments uses HTTP Message Signatures. For each request, the app builds a "signature base" string and signs it with the device key:

<CodeBlock
  language="typescript"
  title="src/op/signatures.ts (simplified)"
  code={`const components = ['@method', '@target-uri']
  if (headers['authorization']) components.push('authorization')
  if (body) components.push('content-digest', 'content-length', 'content-type')

  const params = '(' + components.map((c) => '"' + c + '"').join(' ') + ')'
    + ';keyid="' + key.keyId + '";created=' + Math.floor(Date.now() / 1000)

  const base = components.map((c) => '"' + c + '": ' + valueOf(c)).join('\\n')
    + '\\n"@signature-params": ' + params

  headers['signature-input'] = 'sig1=' + params
  headers['signature'] = 'sig1=:' + toBase64(ed.sign(utf8(base), key.privateKey)) + ':'`}
/>

The `content-digest` header is `sha-512=:<base64>:` of the JSON body. Signatures are easy to get wrong, so the unit tests check our output with `@interledger/http-signature-utils`, the same library Rafiki uses to validate signatures.

## Step 3: Add the key to the wallet, automatically

The auth server must find the device key in the wallet's `jwks.json`. Open Payments has no API to register a key, so each wallet does it in its own way. On the Test Wallet you can paste the key on the **Developer Keys** page. That works, but we wanted to skip the copy and paste.

The Web Monetization extension solves this with a content script that runs inside the logged-in wallet page. A WebView lets us do the same thing. The app opens the Developer Keys page and injects a small script. If the user is not logged in yet, the wallet shows its login page first.

<CodeBlock
  language="javascript"
  title="src/device/testWallet.ts (injected script, simplified)"
  code={`// Runs inside https://wallet.interledger-test.dev, so the wallet's own
  // session cookie authenticates these calls.
  const api = 'https://api-' + location.host
  const res = await fetch(api + '/accounts?include[]=walletAddresses&include[]=walletAddressKeys',
    { credentials: 'include' })
  const accounts = (await res.json()).result
  // ... find the account and wallet address that match ours, then:
  await fetch(api + '/accounts/' + accountId + '/wallet-addresses/' + walletAddressId + '/upload-key', {
    method: 'POST',
    credentials: 'include',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ base64Key: btoa(JSON.stringify(jwk)), nickname: 'Rafiki Upclose mobile' })
  })
  window.ReactNativeWebView.postMessage(JSON.stringify({ type: 'key-upload', ok: true }))`}
/>

The app never sees the password or the cookie. When the script reports success, the WebView closes and the app checks `jwks.json` to confirm the key is there.

## Step 4: Connect the wallet (verify ownership)

Now the app has a key on the wallet. But does the user really own this wallet address? Open Payments has a flow for this: [verify wallet address ownership](https://openpayments.dev/guides/verify-wallet-address-ownership/). It is an interactive grant with a `subject` instead of an `access_token`. It gives no payment rights. It only asks the wallet: "is this user the owner of this address?"

<CodeBlock
  language="typescript"
  title="src/op/connect.ts"
  code={`const wallet = await client.getWalletAddress(walletAddressUrl)
  const grant = await client.requestGrant(wallet.authServer, {
    subject: { sub_ids: [{ id: wallet.id, format: 'uri' }] },
    interact: {
      start: ['redirect'],
      finish: { method: 'redirect', uri: 'rafikiupclose://op/finish', nonce }
    }
  })
  // open grant.interact.redirect in the WebView ...`}
/>

The app opens `grant.interact.redirect` in the same WebView. The user is already logged in from Step 3, so there is no second login. The Test Wallet confirms ownership by itself after a few seconds. Then the app checks the redirect `hash` and continues the grant. The response contains `subject.sub_ids` with the confirmed address.

<ImageBlock
  src="/img/foundation-blog/2026-10-15/connect-ownership.png"

Now the wallet is connected. This is done only once.

## Step 5: Send money to a contact

Each payment uses its own interactive grant. It is a normal checkout: the user sees the exact amount and approves it. The flow has three parts.

**Prepare.** The app creates an incoming payment at the receiver's wallet, then a quote at your wallet, then asks for an outgoing payment grant that is limited to **exactly** this quote:

<CodeBlock
  language="typescript"
  title="src/op/checkout.ts (prepareCheckout)"
  code={`// 1. Incoming payment at the receiver (non-interactive grant)
  const incomingGrant = await client.requestGrant(receiver.authServer, {
    access_token: { access: [{ type: 'incoming-payment', actions: ['create', 'read', 'complete'] }] }
  })
  const incomingPayment = await client.createIncomingPayment(
    receiver.resourceServer, incomingGrant.access_token.value, receiver.id)

  // 2. Quote at the sender (non-interactive grant)
  const quote = await client.createQuote(sender.resourceServer, quoteToken, {
    walletAddress: sender.id, receiver: incomingPayment.id, method: 'ilp',
    debitAmount: { value: '100', assetCode: 'USD', assetScale: 2 } // 1.00 USD
  })

  // 3. Outgoing payment grant (interactive), for this payment only
  const grant = await client.requestGrant(sender.authServer, {
    access_token: {
      access: [{
        type: 'outgoing-payment',
        actions: ['create', 'read'],
        identifier: sender.id,
        limits: { debitAmount: quote.debitAmount, receiver: incomingPayment.id }
      }]
    },
    interact: {
      start: ['redirect'],
      finish: { method: 'redirect', uri: 'rafikiupclose://op/finish', nonce }
    }
  })`}
/>

**Approve.** The app opens `grant.interact.redirect` in the WebView. The user sees "just dollars is requesting access to $1.00" and taps **Accept**. The wallet redirects to our finish URI. The WebView catches it before loading it, and closes:

<CodeBlock
  language="typescript"
  title="src/components/WalletWebView.tsx"
  code={`<WebView
    source={{ uri: redirectUrl }}
    originWhitelist={['*']} // so our custom scheme reaches the handler below
    onShouldStartLoadWithRequest={(request) => {
      if (request.url.startsWith('rafikiupclose://op/finish')) {
        onFinish(parseQuery(request.url)) // { interact_ref, hash } or { result: 'grant_rejected' }
        return false // don't load it; the modal closes
      }
      return true
    }}
  />`}
/>

**Pay.** The app checks the `hash`, continues the grant to get an access token, and creates the outgoing payment:

<CodeBlock
  language="typescript"
  title="src/op/checkout.ts (completeCheckout)"
  code={`// hash = base64(sha256(clientNonce + '\\n' + interact.finish + '\\n' + interact_ref + '\\n' + authServer))
  if (!verifyInteractionHash({ clientNonce, asFinishNonce, interactRef, grantEndpointUri, receivedHash })) {
    throw new Error('Interaction hash mismatch')
  }
  const finalized = await client.continueGrant(continueUri, continueToken, interactRef)
  const payment = await client.createOutgoingPayment(sender.resourceServer, finalized.access_token.value, {
    walletAddress: sender.id,
    quoteId: quote.id
  })`}
/>

Always check the `hash`. It proves that the redirect really comes from your wallet's auth server and belongs to this grant.

## Step 6: Complete the incoming payment

This step is easy to forget. We fixed the amount on the **sender** side (`debitAmount`), so we created the incoming payment **without** an `incomingAmount`. In this case the receiver's wallet does not know when the payment is finished. The incoming payment stays open until it expires.

The fix is in the [docs](https://openpayments.dev/sdk/incoming-complete/): when you are done sending, call `POST {incomingPayment}/complete`. For this you need the `complete` action on an incoming payment grant. Incoming payment grants are non-interactive, so the app asks for a fresh one when it needs it:

<CodeBlock
  language="typescript"
  title="src/op/checkout.ts (settleCheckout, simplified)"
  code={`const grant = await client.requestGrant(receiverAuthServer, {
    access_token: { access: [{ type: 'incoming-payment', actions: ['read', 'complete'] }] }
  })
  const token = grant.access_token.value

  // Wait until the receiver got the quoted amount
  let incoming = await client.getIncomingPayment(incomingPaymentId, token)
  while (BigInt(incoming.receivedAmount.value) < BigInt(quote.receiveAmount.value)) {
    await sleep(1000)
    incoming = await client.getIncomingPayment(incomingPaymentId, token)
  }
  await client.completeIncomingPayment(incomingPaymentId, token) // POST .../complete`}
/>

A small trap we found: the outgoing payment has a `sentAmount`, but Rafiki gives it in the **sender's** currency. If you compare it with `receiveAmount` (receiver's currency), a USD to COP payment never looks finished. Check delivery on the receiver side instead: the incoming payment's `receivedAmount`, in the receiver's currency.

## Step 7: History and live status

The **History** tab lists every transfer made from the app. Tap one to see its live status from the wallet: completed, processing or failed, and how much was delivered.

<ImageBlock
  src="/img/foundation-blog/2026-10-15/history-and-detail.png"
  mobileSrc="/img/foundation-blog/2026-10-15/history-and-detail-mobile.png"
  alt="Left: the History tab with two transfers. Right: the detail of a 3.97 USD to 12652.37 COP transfer, marked as completed, with the receiver's incoming payment completed"
  needsFullView={true}
/>

To read the payment later, the app keeps the payment's grant in the Keychain. This is safe: the grant is limited to that exact payment, which is already spent, so it cannot move more money. Access tokens expire after 10 minutes. When that happens, the app rotates the token with the grant's `manage` URL, without asking the user:

<CodeBlock
  language="typescript"
  title="src/op/payment-status.ts"
  code={`try {
    return await client.getOutgoingPayment(paymentUrl, grant.accessToken)
  } catch (error) {
    if (!isExpiredToken(error)) throw error // 401, or 403 "Inactive Token"
    const { access_token } = await client.rotateToken(grant.manageUrl, grant.accessToken)
    return await client.getOutgoingPayment(paymentUrl, access_token.value)
  }`}
/>

The detail page also completes the incoming payment if it is still open, for example when the user closed the app too early.

## Things we learned

- **Only `redirect` is supported.** Both for starting the interaction and for finishing it. You can check it on any auth server at `/discovery`.
- **Start and finish in the same browser.** Rafiki checks a session cookie at `/interact/.../finish` that it set at the start. If the consent page moves to another browser or app in the middle, the grant fails with `invalid session`.
- **A WebView keeps the login, the system browser does not let you script.** `ASWebAuthenticationSession` (iOS) and Custom Tabs (Android) share cookies with Safari or Chrome, and they are the recommended option for real login. But you can't inject a script into them, so automatic key upload is not possible there.
- **The consent screen shows the client name.** Here the client is the user's own wallet address, so the screen says "just dollars is requesting access to $1.00". The Test Wallet shows the amount, but not the receiver.
- **Complete the incoming payment.** If there is no `incomingAmount`, nobody else will.
- **Check delivery on the receiver side.** `sentAmount` uses the sender's currency.
- **Directed identity does not replace key upload.** The newer `client: { jwk }` option sends the public key in the request body, but it only works for non-interactive grants (incoming payments and quotes). Outgoing payments still need a key in `jwks.json`.
- **iOS 27 needs the scene life cycle.** With the iOS 27 SDK, apps that don't use it crash at launch. Expo SDK 57 already has the scene delegate; the repo includes a small config plugin that enables it.

## What to build at the hackathon

Some ideas, from easy to hard:

- **Request money**: create an incoming payment with an `incomingAmount` and share it as a QR code.
- **Split the bill**: send to several contacts with one confirmation each.
- **Recurring payments**: ask for an outgoing payment grant with an `interval` (for example `R/2026-10-18T00:00:00Z/P1M`) and pay every month without new consent. Our [subscriptions PoC](/blog/subscriptions-with-open-payments-poc/) shows this on a server.
- **Full wallet history**: ask for a read-only grant (`outgoing-payment` with `list` and `read`) and show all payments, not only the ones made from the app.
- **Android**: the code is cross-platform, but we only tested it on the iOS Simulator.

## Closing

This PoC shows that a mobile app can work with Open Payments end to end:

1. It keeps its own key.
2. It connects to the user's wallet with a standard ownership check.
3. It sends money with a clear, per-payment approval.
4. It finishes the payment on both sides.

The in-app WebView is the reason the user logs in only once.

The code is in the [PoC repository](https://github.com/TODO/rafikiupclose). It is experimental and meant as a starting point, not a production wallet.
